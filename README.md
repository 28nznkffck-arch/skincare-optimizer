# スキンケア最適化ラボ — 試作 v0.7.0

予算・肌悩み・手間から、基礎化粧品の組み合わせを提案する静的Webアプリです。**メーカー公式製品情報に基づく52商品**を試験登録しています。従来の30商品をすべて残し、今回は優先して**花王ブランド22商品**（キュレル11、ビオレ5、ソフィーナ iP 6）を追加しました。

主要ブランドの現在の登録数：キュレル18商品、ビオレ6商品、ソフィーナ iP 10商品。ビオレUV・ニベア・ニベアUV・肌ラボ・メラノCC・スキンアクア・イハダ・ミノン アミノモイストの既存登録も維持しています。

## 実装済み

- 月額予算、15項目の肌悩み、悩みごとの優先度（最優先・気になる・軽く気になる）を指定
- 初回表示時は肌悩み未選択。選択すると提案を開始し、肌悩みだけの「選択をクリア」にも対応
- 肌質（乾燥・脂性・混合・普通・不明）、敏感肌、好みの使用感（さっぱり・しっとり・とてもしっとり）を指定
- お手入れの手間（手軽に・こだわらない・しっかり）を指定。コストは月予算の上限制約として扱い、採点には混ぜない
- 成分の優先・必須指定
- 必須カテゴリ（洗顔、保湿、UV）と任意カテゴリ（化粧水、美容液）を組み合わせて探索
- 52商品への増加に合わせ、通常画面・デバッグの首位候補探索を全件ソート不要の高速モードへ変更。デバッグでの予算不足判定は最小必要月額を厳密に探索
- 手軽さの評価は追加ステップへの小さな負担として扱い、化粧水の一律除外を避ける
- 商品単位で固定・除外。合わなかった理由をブラウザ内に保存
- 1品だけ入れ替え、月額差額と組み合わせ全体の評価差を比較。全体の最高得点より高くなる候補だけを表示する仕様を修正し、得点が下がる代替品も明示して選択可能。固定品は入れ替え不可、変更後は手動選択と表示して自動選定へ戻せる
- おすすめを複数保存。保存した組み合わせごとに名称・月予算・各商品の購入価格・推定使用回数・1日使用回数を編集して月額と予算残額を再計算
- 全商品DBの価格・使用量のデバッグ画面を別ウィンドウで開く。検索・カテゴリ絞り込み・25件ずつのページ表示に対応。1回の使用量（mL/g）を編集すると内容量から1本の使用回数を再計算できる
- **マツキヨココカラオンラインの税込価格をJAN一致で47/52商品に登録**（2026-11-06時点）。価格・販売元・販売ページ・確認日を保存。確認できない5商品は仮価格のまま
- **30商品に使用量の根拠を追加**。21商品にはメーカー・販売店記載の使用可能期間から、基準使用頻度で逆算した「約何回分」を登録。残りは使用量の目安（プッシュ・直径）のみ確認できる場合を分離。根拠がない回数は仮値として維持
- デバッグ画面に現在の自動選定・**項目ごとの採点内訳**・各商品の**採用／不採用理由**を表示。特定商品を必ず採用して組み合わせ全体を再計算し、点数差・月額差・採用時の商品一覧を比較できる
- デバッグ画面で商品ごとの肌悩み別の仮スコア、メーカー公式情報の確認段階、確認済み有効成分、配合濃度の登録有無を閲覧できる
- メーカー公式の情報確認に対する小さな加点を導入。効能の強さとは混ぜず、選定される商品数を増やす誘因にならないよう平均確認レベルを利用
- 注意事項はサイトの下部へ集約
- 選定条件・共通商品補正・保存した組み合わせを `localStorage` に保持（バックエンドへの送信なし）。保存プランは共通補正から独立しており、選定条件リセットでも消えない

## データの区分（重要）

| データ | 状態 |
| --- | --- |
| 商品名、内容量、メーカーの商品URL | 公式サイトで照合済み |
| JAN | 公式に確認できたものを登録。イハダの2商品は未確認のため空欄 |
| 主要成分、製品用途の概要 | 公式サイトから要点を抜粋。全成分ではない |
| 価格 | `data/pricing.json` にJAN一致のマツキヨココカラオンライン税込販売価格47件を登録。購入日や店舗による変動あり。未確認5商品は `demoPrice` の仮値 |
| 1本あたり使用回数 | `data/usage.json` に記載期間（例：朝夜使用3か月）と基準頻度のある21件を逆算登録。期間のない商品は `demoUses` の仮回数。1回量（mL/g）は「内容量÷使用回数」の参考逆算値で、実測値ではない |
| 1日使用頻度 | 現行値はユーザーが変更できる計算前提。メーカーが想定する頻度と異なることがある |
| 肌悩みへのスコア | アルゴリズムの仮の重み。実際の効果や安全性の予測ではない |
| 敏感肌向け・使用感タグ | 初期カタログの暫定タグ。個人の刺激や使用感を保証しない |
| `evidence.activeIngredients` | メーカー公式で有効成分表示を確認できたものだけ登録。単なる主要成分リストとは別 |
| `evidence.concentrations` | 成分名・数値・単位・公開出典URLが揃った場合のみ登録。**不明値を0%と扱わない** |

肌悩みの15項目はUIで選べます。今回、花王の薬用商品を含む追加SKUについて「シワ改善」「乾燥による小じわ対策」「シミ・そばかす予防」「皮脂・角栓洗浄」「ハリ感」の効能・用途を区別して仮スコアを付与しました。ただし**スコアは商品間の比較用に手動で定めた仮値**です。特に「乾燥による小じわを目立たなくする」は医薬部外品の「シワ改善」とは区別し、後者の点数を与えていません。赤み・色ムラなど、登録に足る判断根拠のない項目は未採点と表示します。

日焼け止めのスコアについても監査し、従来の「くすみを改善する」かのような点数を削除。紫外線による**新たなシミ・そばかすの予防**の評価へ統一しました。既存のシミ・色むらの改善とは区別しています。

メーカーが処方を更新する場合があるため、将来は処方版・出典確認日・全成分データをそれぞれ保持し、変更検知と再検証が必要です。Amazon/@cosmeのスクレイピングは行っていません。

### デバッグ画面の使い方と判定原則

1. メイン画面で肌悩み・予算・肌質などの条件を設定し、「商品DB・使用量を検証」を開く。
2. 上部の「最良候補の採点内訳を見る」で、各悩みへの適合スコア・手間コスト・肌質・使用感・情報公開加点の計算を確認する。
3. 商品を検索し「この商品の採否理由を検証」を押す。最良候補と、その商品を固定したときの最良候補を再探索して比較する。除外設定・他商品の固定・予算超過も別の理由として表示する。
4. デバッグ画面の価格・1回の量・使用回数を変更すると、メイン画面の自動選定でも新しい月額が使われる。1回の量と使用回数はどちらかを変更すると他方を内容量から逆算する。保存済みの組み合わせは別の独立した記録なので勝手に変更されない。

情報公開の確認レベルは `0:公式情報の登録なし` / `1:メーカー公式製品情報を確認` / `2:公式の有効成分名を確認` / `3:公式の配合量数値と出典を確認`。`evidence.officialSource: true` はメーカー公式出典の確認後にのみ設定する。今回追加した15商品には、公式の医薬部外品有効成分（該当商品のみ）を登録。ミノンや極潤ヒアルロン液などの**化粧品の保湿成分は医薬部外品の有効成分として記録しない**。濃度数値は公式の根拠を確認できないため、登録していない。**「未調査」「未登録」は「配合なし」「非公表」と同一視しない。**

情報公開のボーナスは採点上限が1.05点（1商品あたりの確認レベルの平均 × 0.35）という小さい補助点。肌悩みや処方の適合性・製品の効果を示すものではなく、公式情報が後日登録された場合はスコアが変化しうる。予算は適合点数ではなく必須の上限制約として別管理する。

## 構成

```
dist/
  index.html
  styles.css
  app.js                # UI・状態管理
  catalog-data.js       # JAN一致の小売価格・使用期間目安を商品に結合
  optimizer.js          # データと独立した選定・費用計算
  plans.js              # 保存プランのスナップショット・月額計算
  debug.html            # 商品DBの別画面
  debug.js              # 検索・ページ表示・共通商品補正・選定再計算
  debug-analysis.js     # デバッグ用の採点内訳・採否理由・情報公開状況の表示
  data/products.json    # 商品データベース（別ファイル）
  data/pricing.json     # 小売サイトの税込価格と出典（47件）
  data/usage.json       # 使用量・使用期間の記載と出典（30件）
tests/
  optimizer.test.mjs
```

商品を増やすには `dist/data/products.json` の `products` 配列へレコードを追加します。`id` は一意、`category` は `cleanser / toner / serum / moisturizer / sunscreen` のいずれかです。`sourceUrl` は必須、`demoPrice` と `demoUses` は出典のない場合のみ仮値として使われます。価格はJAN一致を検証してから `pricing.json` に追加します。1回量はプッシュ数や「直径3cm」だけからmL/gを推定せず、使用期間の参考値があれば `usage.json` に登録して算出します。

## ローカル確認

Node.jsがある環境で `npm test`。静的配信は `npx serve dist` 等の任意のHTTPサーバーで可能です。`file://` 直接起動だとJSONの読み込みが制限されるブラウザがあります。

GitHub Pagesでは、`main` ブランチの `/ (root)` を公開元に設定してください。リポジトリ直下の `index.html` が `dist/` に転送し、アプリを表示します。Pagesの公開設定自体は別途有効化が必要です。
